# Pre-project Report: Application of Digital Signatures for the Document Approval Process

## 1. Introduction
In modern organizational workflows, the transition from paper-based to digital document approval processes introduces significant security challenges. When documents are transmitted over insecure networks, they are vulnerable to interception, unauthorized modification, and identity spoofing. In a traditional scenario, the receiver (Bob) has no inherent mathematical guarantee that a document genuinely originated from the claimed sender (Alice) or that the content remained unaltered in transit.

To mitigate these risks, this project proposes the implementation of a **Digital Signature** application. This cryptographic solution is designed to provide three core security guarantees:
*   **Message Authentication:** Assures the receiver that the document was genuinely authorized by the specific user holding the private key.
*   **Data Integrity:** Guarantees that the document has not been altered, tampered with, or corrupted during transmission.
*   **Non-repudiation:** Prevents the signer from falsely denying that they signed the document, as the signature is uniquely tied to their cryptographic identity.

## 2. Cryptographic Background
The proposed application relies on two fundamental cryptographic primitives: Asymmetric (Public-Key) Cryptography and Cryptographic Hash Functions.

### 2.1. Asymmetric Cryptography and RSA
Unlike symmetric ciphers that use a single shared key, asymmetric cryptography utilizes a key pair: a private key ($k_{pr}$) kept secret by the owner, and a public key ($k_{pub}$) distributed openly. For digital signatures, the roles of the keys are reversed compared to encryption. The sender "encrypts" (signs) the data using their private key, and the receiver "decrypts" (verifies) it using the sender's public key.

This project will utilize the **RSA Signature Scheme**, which relies on the computational difficulty of factoring large integers. An RSA key pair is generated by choosing two large prime numbers, $p$ and $q$, to compute the modulus $N = p \cdot q$. The public exponent is $e$, and the private exponent $d$ is derived such that $e \cdot d \equiv 1 \pmod{(p-1)(q-1)}$. 
*   **Public Key:** $k_{pub} = (N, e)$
*   **Private Key:** $k_{pr} = d$

To ensure robust security, the modulus $N$ must be at least 1024 bits (preferably 2048 bits). Furthermore, a padding scheme must be applied before signing to prevent **Forgery Attacks**, where an attacker might mathematically derive a valid signature for a random message.

### 2.2. Cryptographic Hash Functions
Applying the RSA signing operation directly to a large document is computationally prohibitive, introduces severe message overhead, and creates security vulnerabilities. To resolve this, a **Hash Function** ($h$) is employed. 

A hash function compresses a message of arbitrary length into a fixed-length digest or "fingerprint" (e.g., 256 bits for SHA-256). To be considered secure for digital signatures, the hash function must exhibit:
1.  **Preimage Resistance (One-wayness):** Given a hash $y$, it is computationally infeasible to find the original message $x$ such that $h(x) = y$.
2.  **Second Preimage Resistance:** Given $x$, it is infeasible to find another message $x'$ such that $h(x) = h(x')$.
3.  **Collision Resistance:** It is infeasible to find any two distinct messages $x$ and $x'$ that produce the same hash $h(x) = h(x')$.

Because the hash output is highly sensitive to input changes (the avalanche effect), even a single-bit alteration in the document will completely change the resulting fingerprint, thereby breaking the signature verification.

## 3. Methodology & System Architecture
The application will simulate a secure document exchange between two parties: the Signer (Alice) and the Verifier (Bob). The architecture consists of two main phases: Signature Generation and Signature Verification.

### 3.1. Phase 1: Signature Generation (Alice)
When Alice wishes to approve and send a document $x$ to Bob, the application performs the following operations:
1.  **Hashing:** The application processes the document $x$ through a hash algorithm (e.g., SHA-256) to produce a fixed-length hash digest: $z = h(x)$.
2.  **Signing:** Alice utilizes her private key, $k_{pr, A}$, to mathematically sign the hash digest $z$. Using RSA, the signature $s$ is computed as: 
    $$s \equiv z^d \pmod N$$
3.  **Transmission:** The application packages the original document and the digital signature together as a tuple $(x, s)$ and transmits it to Bob over the network.

### 3.2. Phase 2: Signature Verification (Bob)
Upon receiving the package $(x, s)$, Bob's system must independently verify its authenticity:
1.  **Re-hashing:** Bob's application extracts the document $x$ and applies the exact same hash function used by Alice to compute a new hash digest: $z' = h(x)$.
2.  **Signature Decryption:** The application takes the received signature $s$ and processes it using Alice's public key, $k_{pub, A}$, to recover the original hash digest $z_{computed}$. Using RSA, this is computed as:
    $$z_{computed} \equiv s^e \pmod N$$
3.  **Comparison (Verification):** The system compares the newly computed hash $z'$ with the decrypted hash $z_{computed}$. 
    *   If $z' = z_{computed}$, the function $ver(x, (s))$ returns `True`. The document is authentic and unmodified.
    *   If $z' \neq z_{computed}$, the function returns `False`. The document is rejected.

## 4. Testing & Simulation Plan
To validate the effectiveness of the application, the project will implement and document the following simulation scenarios:

### 4.1. Scenario 1: Standard Valid Workflow
*   **Action:** Alice signs a valid PDF/TXT contract and sends it to Bob.
*   **Expected Result:** Bob's system successfully retrieves Alice's public key, the hash values match ($z' = z_{computed}$), and the software interface displays a "Signature Valid" status. This confirms Message Authentication and Non-repudiation.

### 4.2. Scenario 2: Man-in-the-Middle (MitM) Integrity Attack
*   **Action:** A malicious actor (Trudy) intercepts the transmission $(x, s)$ between Alice and Bob. Trudy alters a single crucial value in the document $x$ (e.g., changing a payment amount from $1000$ to $9000$) to create an altered document $x_{altered}$. Trudy forwards $(x_{altered}, s)$ to Bob.
*   **Expected Result:** When Bob receives the package, his system hashes $x_{altered}$ to produce $z'_{altered}$. Because of the hash function's collision resistance, $z'_{altered}$ will be radically different from the original $z$ encrypted within $s$. Consequently, $z'_{altered} \neq z_{computed}$. The system will reject the document, successfully demonstrating the enforcement of Data Integrity.

## 5. Conclusion
The proposed application will demonstrate the practical integration of asymmetric cryptography and hash functions to secure digital workflows. By implementing a Digital Signature scheme, the system effectively counters the risks of document forgery and tampering. 

While the cryptographic mathematics provide strong security, the real-world safety of this system relies heavily on Key Management. A future extension of this project will explore the integration of a Public Key Infrastructure (PKI) and Certification Authorities (CAs) to reliably bind Alice's identity to her public key ($k_{pub, A}$), preventing scenarios where an attacker might substitute the public key entirely.
